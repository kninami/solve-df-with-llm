# Validate system clock correctness at event time using paired local-external timestamp anchors

## Summary

Many digital artifacts store both a timestamp generated by the local system clock and a corresponding timestamp originating from an external, less-tamperable source (e.g., a web server's HTTP response header, a synchronization-server timestamp in a Windows Time Service event, or an epoch value embedded in a URL parameter). Where such a paired artifact — a "time anchor" — exists, comparing the two values shows directly whether the system clock was correct (they approximately agree) or skewed (they disagree, with the difference giving the skew) at the exact time the event occurred.

## Details

An event whose own artifacts are themselves time anchors (e.g., a Google search generates cache entries containing both a system-clock last-accessed time and a server-issued HTTP timestamp) is an "anchoring event," letting an examiner make a direct statement about clock correctness at the precise time of that event. An event whose artifacts contain no external timestamp (e.g., a file's creation time) is a "non-anchoring event," and its clock correctness can only be bounded by the nearest time anchors found before and after it, complemented by a search for "time anomalies" (explicit system-time-change log entries, out-of-order sequence numbers, or deviations from expected periodic synchronization intervals) as corroborating evidence. Because a single anchor still leaves residual uncertainty, an examiner should express findings using a graded confidence scale — such as Casey's C-Scale — that accounts for how many independent, tamper-resistant sources agree, rather than treating one matching or mismatching anchor as conclusive proof.

## Examples

- Comparing Chrome cache HTTP response-header timestamps and Chrome history URL-embedded epoch timestamps against the local "last accessed"/"visit_time" fields identified a ~2:55h backdating of a VM's system clock during a simulated Google search.
- Windows Time Service event log ID 261 (`W32time service has set the system time to ...`) functions as a built-in local time anchor by recording both the previous (local) and the synchronization-server-derived (external) system time in the same log entry.
