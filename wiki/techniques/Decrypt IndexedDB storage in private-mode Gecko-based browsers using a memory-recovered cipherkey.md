# Decrypt IndexedDB storage in private-mode Gecko-based browsers using a memory-recovered cipherkey

## Summary

Since Firefox 115.0 (July 2023) and Tor Browser 13.0 (October 2023), Gecko-based browsers support IndexedDB storage in private mode by writing encrypted SQLite database and BLOB files to disk under a randomly named UUID folder, using a per-file 32-byte cipherkey generated by the `CipherKeyManager` class and, per the browser's own documentation, held only in memory for the life of the private session. Because the files remain encrypted with no built-in on-disk key, they are of limited direct evidential value unless the cipherkey can also be recovered — this technique shows that the cipherkey's fixed in-memory structure layout allows it to be located and extracted from a memory dump or a Windows hibernation file, after which it decrypts the files fully.

## Details

Decryption proceeds in three phases. First, a regular-expression search for the fixed 8-byte header pattern preceding each `CipherKeyManager` hashtable entry (distinct, predictable patterns exist for DB-file and BLOB-file entries, since DB filenames are always `Default` and BLOB filenames increment from `1`) yields a set of 32-byte candidate cipherkeys from a memory image. Second, each candidate is bruteforced against the target encrypted file's AEAD authentication tag (ChaCha20-Poly1305) until one decrypts without a MAC verification error, confirming the correct key. Third, the validated cipherkey is applied page-by-page: each encrypted SQLite DB page (0x2000 bytes) stores its Nonce and Initial Vector in the last 32 bytes of the page, while each encrypted BLOB page (0x1000 bytes) stores them in the first 48 bytes, alongside a ciphertext-length field for the final page. Candidate cipherkeys can be searched not only in live RAM but also in a Windows hibernation file (`Hiberfil.sys`), since the "Hibernate" power option (unlike "Fast Startup" or a normal shutdown) writes the full contents of all user-process memory, including the browser's, to disk before power-off. The technique does not work against the Windows pagefile/swapfile or unallocated space, since the paper's experiments found cipherkeys are never paged out of RAM during an active session, and the cipherkey is deliberately deleted from memory the instant the private session ends (browser closed, or PC shut down with no special option or with Fast Startup) — Hibernate mode is therefore the only route to recovery once the browser itself is no longer running.

## Examples

- Recovering the cipherkey for a Firefox private-session IndexedDB DB file from a live physical memory dump by pattern-matching the `CipherKeyManager` hashtable's fixed header fields, then bruteforce-validating candidates against the file's AEAD authentication tag and decrypting all 10 test DB files and 10 BLOB files (10/10 each) in the paper's live-session test case.
- Recovering all 20 encrypted IndexedDB files from a Windows 10 PC that had been fully shut down using the Hibernate power option, by extracting the cipherkey from the resulting `Hiberfil.sys` file rather than from live RAM.
